# Dialogue Record — 2026-09-19

## Scope

Diagnosis and correction of delayed/out-of-order Telegram bot replies.

## Verified observations

**FACT:** Incoming Telegram messages reached Receiver/GitHub promptly.

**FACT:** In the original per-update dispatch architecture, independent GitHub Actions runs started out of order. A later update could be processed before an earlier one.

**FACT:** A durable repository-side queue was introduced to serialize work, but it placed multiple GitHub API reads and commits in every message round-trip.

**FACT:** Live tests still showed replies behaving as though they needed a later event before appearing.

**FACT:** Temporary diagnostics explored `reply_parameters` and direct `sendMessage`; those experiments did not identify the root defect and were removed from the final workflow set.

**DECISION:** Return diagnosis to our own processing path and eliminate unnecessary orchestration.

**DECISION:** Replace the repository-side runtime queue with direct sequential processing:

```text
getUpdates -> isolated consumer -> sendMessage
```

**FACT:** After deployment, `TEST_D` received an immediate reply.

**FACT:** A burst `1 2 3 4 5` received replies in the correct sequence.

**DECISION:** This direct FIFO design is the accepted baseline.

## Important lesson

The prompt arrival of inbound updates had already ruled out the receiving side as the primary defect location. Future debugging must preserve that distinction and start from the first component whose behavior is actually inconsistent with evidence.
