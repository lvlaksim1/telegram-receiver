# Dialogue Record — 2026-09-20

## Scope

Audit of whether the current Receiver still matched the original project goals after the direct FIFO fix.

## Findings

**FACT:** Realtime response and strict ordering were restored by the direct FIFO path.

**OPEN FOUND:** The worker offset existed only in RAM, so a restart could replay already completed updates.

**OPEN FOUND:** The health workflow invoked `getUpdates`, which could compete with the live Receiver for Telegram updates.

**OPEN FOUND:** CI did not directly test FIFO/retry/restart behavior.

## Corrections

**DECISION:** Added a dedicated `receiver-checkpoint` branch with `state/checkpoint.json`.

**DECISION:** Checkpoint persistence occurs after consumer/send completion, outside the visible reply hot path.

**DECISION:** Checkpoint persistence retries in place without re-running consumer or `sendMessage`.

**DECISION:** Health no longer invokes `getUpdates`; it checks credentials/webhook state, checkpoint readability and active Receiver runs.

**DECISION:** Added regression tests for offset recovery, FIFO, checkpoint deduplication, failure ordering and checkpoint retry without resend.

## Remaining limitation

Exactly-once outbound reply semantics are still impossible in the narrow crash interval between successful Telegram `sendMessage` and successful checkpoint persistence. This limitation is explicit and must not be disguised by reintroducing heavy pre-send GitHub persistence.
